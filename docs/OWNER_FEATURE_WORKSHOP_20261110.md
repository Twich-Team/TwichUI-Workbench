# Owner requirements: expanded Feature Workshop

Recorded November 10, 2026 (Mountain time). These are explicit requirements for future expanded feature development. Continue the current Phase A/B milestones first. This clarification does not authorize starting image generation or a new feature orchestration framework during the active overnight campaign.

## Optional references

Feature requests may optionally include screenshots, UI mockups, reference artwork and supporting documents. Preserve the attachments with the request and use them as relevant context during research, planning and implementation, within existing disclosure/access safeguards. Ordinary requests must remain easy to submit without attachments.

## Proposed visual mockups

For meaningful visual changes, optionally offer a generated UI proposal during planning. Where supported, allow the owner to review it, provide ordinary-language feedback, request revisions, and approve the visual direction or proceed under existing authorization. Rendered concept artwork must use an actual supported image-generation capability; text descriptions and fabricated screenshots are not generated mockups. Clearly label proposed artwork separately from the implemented interface. Introduce no unapproved API charges.

## Comparable simulator evidence

When the existing simulator reliably renders the affected addon UI, capture before/after screenshots using the same simulator version, viewport/UI scale, game-state fixtures, relevant addon settings and interaction sequence where possible. Show the real simulator images side by side or through an intuitive comparison control in Results. Keep simulator screenshots distinct from concept mockups and real in-game evidence.

Explain simulator limitations when reliable reproduction is unavailable, retain the need for real in-game verification, and never change production behavior merely to satisfy the simulator.

## Parent features and coherent subtasks

Automatically decompose larger features into coherent subtasks with dependencies, acceptance criteria and a sensible execution order. Show one understandable parent feature and overall progress. Coordinate implementation, testing, recovery and completion without routine owner involvement. Independently implemented subtasks still require integration and checks of the final combined behavior. Prevent duplicate work and conflicting simultaneous edits. Reuse suitable existing application owners rather than adding a new orchestration framework merely because these requirements were recorded.

## Feature-level delivery

Normally deliver related subtasks together in one reviewable feature-level draft PR after the combined implementation passes appropriate checks and applicable publication authority. The final result explains the feature's behavior, changes, completed subtasks, tests, relevant simulator before/after images, limitations, and actual published draft link. Existing source, usage, spending, independent-check, publication and merge safeguards remain.

These requirements are recorded direction, not evidence that attachments, generated mockups, simulator comparisons, automatic feature decomposition or combined feature delivery are already implemented or installed.
