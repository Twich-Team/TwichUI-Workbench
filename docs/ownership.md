## Durable command behavior

`BEGIN IMMEDIATE` acquires the writer lock before revision validation. The busy
timeout is 150 ms per connection; a busy API returns 503 with `Retry-After: 1`.
There is no success acknowledgment on an uncommitted transaction. The browser
preserves the exact payload and ID and offers an explicit retry. A lost response
can be reconciled by task receipt, direct command lookup, or identical resubmission.
Changing a payload under the same ID returns 409. A second ID for the same
review also conflicts. One pending command per task is enforced transactionally.

Each worker tick uses one short transaction for validation, task update,
application audit and command outcome. There are no external operations inside
that transaction. Crashing before commit leaves pending work intact; crashing
after commit leaves a completed audit and prevents repeated application. Multiple
worker processes serialize through SQLite; no stuck in-progress lease exists.
The application audit has one primary key per command. A stale command stays
saved and terminal without changing task state; opening refreshed evidence allows
a new explicitly answered review. Applied or changes-requested tasks do not
silently become executable. Database contention leaves acknowledged pending work
untouched for a later tick. Non-contention storage failure stops the worker for
operator inspection, preserving durable pending work.

SQLite uses local-disk rollback journaling, foreign keys, `synchronous=FULL`,
short transactions and a queue index. Migration/model consistency, transactional
rollback, database integrity and SQLite backup/restore are tested. No telemetry
retention, private artifact storage or production data migration is introduced.
